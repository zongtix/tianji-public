> **分工**：脚本/文档由你写；**真实演练由持有服务器访问权的核验方执行**（你无法访问该 ECS）。所以每个演练项都要交付**可直接执行的脚本 + 预期输出 + 判定逻辑**，而不是只写说明。

## 1. 硬约束（违反即返工）

1. **演练不得波及同宿其他 9 个服务**。允许的手段**仅限**：
   - Redis / RabbitMQ：只对 `tj-remark` 用 **`-D` 参数覆盖端口**后重启，例如 `-Dspring.redis.port=16379`、`-Dtj.mq.port=15673`；改参数前核对 Nacos 是否定义同名配置；
   - MySQL：**`KILL <id>` 且只针对 `information_schema.processlist` 里 `db='tj_remark'` 的连接**（实测 10 个，其它服务各占自己的库）。
   - ❌ **禁止**：`docker stop/restart` 容器、改 Redis/MySQL/MQ 全局配置、`FLUSHALL`、`iptables` 全局规则、动别的库。
2. **不改对外接口、不改 Redis 键名与类型、不引入新依赖**（延续第二批）。
3. **不做自动修复**；仍然只用 `ALERT` 日志报告。
4. **测试数据必须可清理**：所有演练用独立 `userId`（如 `9998`）+ 明确的 `bizId` 段，脚本末尾要给出对应的 MySQL/Redis 清理语句。
5. **测试先行**：本批新增的**判定逻辑**（如压测脚本里的阈值判定、演练脚本里的"是否丢失"断言）必须有单测，且改前为红。
6. **不夸大结论**：任何拿不到实测数据的项，在交付文档里写"未实测 + 原因"，**不得**用推理代替实测（例如"断电 ≤1s"在没做断电演练前只能说"理论值，未实测"）。
7. **脚本留痕**：演练脚本要写清"注入了什么、预期现象、如何判定通过、如何恢复"，并支持**幂等重跑**。

## 2. 任务分解

### C1 备份机制（当前完全缺失，必须补齐）

**交付**：`scripts/` 下可执行脚本 + 安装说明（cron 表达式）+ **恢复演练脚本**。

要求：
- **Redis**：备份 `appendonly.aof` + `dump.rdb`（宿主路径 `/usr/local/src/redis/data/`）。建议 `BGSAVE` 后复制，**不要**直接 `cp` 正在写入的 AOF（可能不一致）——用 `BGREWRITEAOF`/`BGSAVE` + 复制 RDB，或 `redis-cli --rdb` 直取；
- **MySQL**：`mysqldump --single-transaction`（当前库 `tj_remark` 等）+ 记录 binlog 位点，供 PITR；
- **保留策略**：保留 N 份（建议 7 天），超期自动删；备份目录**不要**放在同一块盘以外就不算异地——如果做不到异地，文档里**明说这是同盘备份，宿主机故障仍需依赖云盘快照**；
- **恢复演练脚本**：把一个备份恢复到**临时目录/临时实例**并校验行数，证明备份是**可恢复的**（"备份存在"≠"能恢复"）；
- **不要动现有数据**：只读+复制，不 `DEL`、不改配置。

**验收**：脚本能在服务器上跑通；恢复演练能证明备份可用；文档写明同盘风险。

### C2 故障注入与恢复演练（脚本化）

三组演练，**每组都要"注入 → 观察预期现象 → 恢复 → 验证收敛"**，并输出可粘贴的证据日志。

| 演练 | 注入方式（唯一允许） | 预期现象 | 恢复验证 |
|---|---|---|---|
| **R1 Redis 不可用** | `-Dspring.redis.port=16379` 重启 remark | 启动时 `redissonClient` Bean 创建失败、进程非零退出、HTTP 000；仅运行中断线的独立场景才验证接口 503 | 去掉参数重启 → 接口 200、`XLEN` 收敛、无新 ALERT |
| **R2 MySQL 不可用** | 循环 `KILL` `db='tj_remark'` 的连接（核验方已有脚本，你可复用/改进） | 落库失败 → `处理点赞缓存批次失败` + 退避；**消息留在 Stream（`XLEN` 不归零）**；`failCount` 增长 | 停止 KILL → 自动补落 → `XLEN=0`、表内数据完整 |
| **R3 MQ 不可用** | `-Dtj.mq.port=15673` 重启 remark | 写接口仍 `200`（Redis 侧成功）；**消费侧发布失败 → 退避重试 → Stream 积压**；`XLEN`/`lagMs` 增长；延迟 ALERT 一致性待复核 | 去掉参数重启 → 退避恢复 → 全部落库 + MQ 补发 → `XLEN=0` |

**关键判据**：演练全程**不得丢已接受的消息**——R2/R3 结束后，落库行数必须等于成功接受的请求数（差额只能是"失败返回 503 的那些"）。

**断电（R4）**：如果你无法安全模拟断电（共享环境不允许），**明确写"未实测"**，不要用推理冒充实测；可以在文档里给出"若要在隔离环境验证，步骤是什么"。

### C3 峰值压测（限速、算水位）

**目的**：补上 B4 水位推导里 Codex 自己标注的缺口——`"实际超量还需用峰值写入速率测出"`。

要求：
- **压测目标**：`POST /likes`（走 Lua + Stream 的完整链路）；
- **必须限速**：从 ~50 QPS 起阶梯上升，每档持续 30~60 秒；**每档都要采样**：宿主 `free -m`、Redis `INFO memory used_memory`、`XLEN`、`XPENDING`、接口 P95 延迟；
- **安全红线（硬性）**：宿主 `available` 低于 **500MB** 或 Redis `used_memory` 超过宿主可用内存的 50% → **立刻停止**，这既是压测安全线，也是水位推导的输入；
- **数据隔离**：用独立 `userId` + 独立 `bizId` 段，压测结束后给出清理语句；
- **输出**：TPS / 延迟分位 / 最大积压 / 内存增长曲线 / **推算出的拒写水位是否与 50,000 相符**（不符就给新值 + 推导）。

### C4 生产配置核查（写文档，不改配置）

- **NOTE 消费链路**：核实当前状态（`remark.note.liked.times.queue` 有队列无消费者、`tj_learning` 无 note 表），给出"NOTE 上线还需要哪些改动"的清单（**本批只核实，不实现**）；
- **发布配置**：`bootstrap.yml` 的 `spring.profiles.active`（当前默认 `dev`，实际用 `local`）与生产 profile 的差异清单；
- **`maxmemory` 未设置**：给出结论——为什么不设、有何风险（**该 Redis 被 10 个服务共用，B4 只保护 remark**）、建议值怎么定。**不要直接改**。

### C5 发布与回退步骤（文档）

必须回答：
1. 发布顺序（先删 `READY` 还是先停写？参考第一批的"先停写 → 排空 → 重建"）；
2. **回退时 Stream 里还有未落库记录怎么办**（第一/二批都踩过这个点）；
3. 回退后如何验证一致（复用第一批的 `comm -3` 逐行比对方法）；
4. 灰度/多实例场景下的注意事项（`WORKER_LOCK`、`INITIALIZE_LOCK` 的行为）。

### C6 数据丢失范围结论表（最终交付）

把口径落成一张表，**每行都要标明证据来源**（实测 / 理论 / 未实测）：

| 场景 | 目标 | 依据 |
|---|---|---|
| 计划内停写并排空 | 0 丢失 | 第一批实测 |
| 应用进程崩溃（Redis 存活） | ≈0 | 第一批 PEL 接管实测 |
| Redis 断电 | ≤1s（**待 R4 证实**） | AOF `everysec` 理论值 |
| Redis 被重建（`READY` 丢失） | 需人工重启 | 第二批实测（无自动重建入口） |
| 积压风险 | 由拒写水位封顶 | B4 水位 + C3 压测实测量 |

## 3. 交付格式

1. **脚本清单**：路径 + 用途 + 前置条件 + 一行示例命令；
2. **演练报告**：每组演练的"注入/预期/实际/是否通过/证据"，**实际输出要贴原始日志或命令结果**；
3. **压测报告**：分档数据表 + 安全红线触发情况 + 水位结论；
4. **未实测项清单**：明确列出 + 原因 + 若要实测需要什么条件；
5. **测试结果**：新增判定逻辑的单测"先红后绿"输出与总数。

## 5. 明确不做的事

- 不实现 NOTE 消费者（只核实 + 列待办）；
- 不改 Redis/MySQL/MQ 的全局配置与容器（共享环境）；
- 不引入 Prometheus/Grafana/告警通道；
- 不做跨服务对账（B5-2 的 `retrySnapshots` 漏洞留给后续）；
- 不顺手格式化/重命名/统一行尾符。
