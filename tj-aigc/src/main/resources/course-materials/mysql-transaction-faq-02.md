# MySQL 事务隔离与锁等待 FAQ

> 演示资料：本文由 DeepSeek 依据公开的 MySQL/InnoDB 通识原创编写，仅用于天机学堂 AI 能力演示，不是任何真实售卖课程的官方讲义，也不代表课程实际授课内容。核验日期：2026-10-31。

## 事务与隔离级别

InnoDB 支持四种隔离级别，默认是可重复读（REPEATABLE READ）。
隔离级别越高，一致性越强，但并发冲突和锁等待也可能增加。
读已提交（READ COMMITTED）下每次查询看到最新提交的数据，可重复读在事务内保持快照一致。

## MVCC 与快照读

MVCC 通过版本链和 Read View 实现快照读，普通 SELECT 通常不加锁，直接读取可见版本。
快照读减少了读写冲突，但当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）仍要加锁并读取最新版本。

## 行锁与间隙锁

InnoDB 行锁基于索引实现；没有合适索引时，可能退化为更大范围的锁甚至表级锁。
可重复读下的间隙锁用于防止幻读，会锁住索引记录之间的间隙，可能增加锁等待。
锁等待和死锁的排查要结合事务顺序、索引使用和隔离级别，不能只看单条 SQL。

## 死锁

两个事务以相反顺序持有并等待对方的锁，就形成死锁。InnoDB 检测到死锁后会回滚其中一个事务。
减少死锁的常见做法：统一加锁顺序、缩短事务、避免大范围更新、为条件列建立合适索引。

## 热点行更新

库存扣减、计数累加这类高频更新同一行的场景，容易形成热点行竞争。
表现为大量锁等待和超时。缓解方式包括缩短事务、批量合并更新、拆分计数行，
或者在业务层做排队和限流。热点行问题不能仅靠调大锁等待超时解决。

## 与缓存的关系

数据库事务保证的是持久化和一致性边界，缓存不参与数据库事务。
先提交事务再删除缓存，仍要处理删除失败和并发读回填的问题。
缓存的一致性问题应单独设计，不能假设数据库事务会自动覆盖缓存状态。
