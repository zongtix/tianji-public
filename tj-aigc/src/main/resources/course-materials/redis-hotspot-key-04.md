# 热点 Key 的识别与治理

> 演示资料：本文由 DeepSeek 依据公开的 Redis 缓存通识原创编写，仅用于天机学堂 AI 能力演示，不是任何真实售卖课程的官方讲义，也不代表课程实际授课内容。核验日期：2026-10-31。

## 什么是热点 Key

热点 Key 指在短时间内被大量请求访问的缓存 key，例如热门课程详情、活动首页、榜单第一位数据。
热点 Key 的风险是：单个 key 的访问量占据大部分流量，一旦失效或所在节点异常，压力会集中释放。

## 识别方式

- 监控单 key 的访问 QPS 和命中率，观察是否存在明显高于均值的 key；
- 关注缓存节点 CPU、网络带宽和慢查询，定位流量集中的节点；
- 在业务侧记录高访问量对象的 ID，结合日志抽样统计。

识别应基于观测数据，不能只看业务猜测。热点也会随时间变化，需要持续观察。

## 常见治理手段

- 本地缓存：在应用进程内缓存一层热点数据，减少对 Redis 的集中访问；
- key 拆分：把一个热点 key 复制成多个副本，请求按用户或随机数分散读取；
- 读写分离与分片：把热点 key 分散到不同节点，避免单节点过载；
- 限流与降级：流量超过容量时保护数据库和后端服务，返回降级内容；
- 异步预热：在流量高峰前提前加载热点数据，减少冷启动回源。

这些手段各有代价：本地缓存会引入多实例数据不一致，key 拆分增加更新复杂度，
限流会影响部分用户，需要结合业务容忍度选择。

## 热点 Key 与击穿、雪崩的关系

热点 Key 不必然导致击穿，但两者经常一起讨论：
热点 key 过期时容易形成集中回源，属于击穿场景；
大量热点 key 同时失效或缓存节点故障，则可能演变为雪崩。
治理时应先识别热点，再决定用互斥锁、逻辑过期还是多级缓存。

## 逻辑过期

逻辑过期指缓存值本身带一个过期时间字段，物理上不设置 TTL。
读取到逻辑过期的数据时，先返回旧值，再由一个后台任务或持锁请求异步重建。
好处是避免大量请求等待重建；代价是可能短时间返回旧数据，需要业务能接受。

逻辑过期适合读多写少、可容忍短暂陈旧的热点数据，不适合强一致要求的场景。
