# 缓存击穿与互斥锁 FAQ

## 这份资料的范围

本文只讨论「缓存击穿」以及用互斥锁重建缓存这一种处理方式。
缓存穿透、缓存雪崩、热点 Key 分片等内容在其他篇目单独说明，本文不展开。

## 什么是缓存击穿

缓存击穿指某个被大量请求访问的热点 key 在缓存中过期的瞬间，
原本由缓存承担的读取流量同时落到数据库上，数据库压力突然升高。

关键点在「一个热点 key」和「过期瞬间」：

- 击穿针对的是单个高访问量 key；
- 触发条件是这个 key 在缓存里恰好失效；
- 数据本身通常仍存在于数据库中，只是缓存暂时没有。

如果热点 key 一直有效、缓存里始终有值，通常不会出现这种「同一时刻集中回源」的击穿形态。
但这不代表永不过期是万能做法，长期不更新的缓存仍要单独处理一致性问题。

## 为什么用互斥锁重建缓存

常见做法是：缓存未命中时，先尝试获取一个互斥锁，
只有拿到锁的请求去查数据库并写回缓存，其余请求短暂等待后重新读缓存。

这样做的目的不是给业务数据加锁，而是把「回源重建」这件事收敛成一次，
避免大量请求同时查库。示例里强调互斥锁，而不是只说「加锁就行」，原因有三点：

1. 锁保护的是缓存重建动作，不是整段业务逻辑，锁范围要尽量小；
2. 抢锁失败应当等待或快速失败，不能让所有线程排队查库；
3. 锁必须带超时或自动续期，否则持锁进程异常会让后续请求长期阻塞。

只写一句「加锁就行」，容易把锁加到查询、序列化、远程调用等慢操作外面，
既扩大冲突范围，也可能因为锁无超时造成新的可用性问题。

## 互斥锁写法的注意点

- 使用 SET key value NX PX timeout 这类原子写法抢锁，不要先 GET 再 SET。
- 锁的值使用请求唯一标识，释放时校验值，避免误删别人的锁。
- 锁超时时间要覆盖重建耗时；重建可能很久时考虑续期或后台异步重建。
- 抢锁失败后等待一小段时间再读缓存，而不是一直自旋或直接穿透到数据库。
- 缓存重建失败时也要释放锁，并记录失败原因，不能把异常当成空结果缓存起来。

## 常见追问

问：热点 key 永不过期，还需要讨论击穿吗？
答：本文讨论的击穿前提是热点 key 过期。若缓存永不主动过期，集中回源的触发点会改变，
但仍要处理数据更新、一致性以及进程重启后缓存为空等情况，不能据此认为问题消失。

问：互斥锁和分布式锁是不是同一个东西？
答：同机多线程可以用进程内锁；多实例部署时，互斥范围要跨进程，才需要分布式锁。
具体边界见《分布式锁的适用边界》。
