# MySQL 索引失效与执行计划 FAQ

> 演示资料：本文由 DeepSeek 依据公开的 MySQL/InnoDB 通识原创编写，仅用于天机学堂 AI 能力演示，不是任何真实售卖课程的官方讲义，也不代表课程实际授课内容。核验日期：2026-10-31。

## 索引与 B+ 树

InnoDB 的主键索引是聚簇索引，叶子节点保存整行数据；二级索引叶子节点保存主键值，
查询非索引列时需要回表。B+ 树让范围查询和等值查询都能保持较少的磁盘访问次数。

## 联合索引与最左前缀

联合索引 (a, b, c) 的可用性取决于查询条件是否从最左列开始连续使用。
只查 b、c 通常无法有效利用该索引；查 a 和 c 时，c 一般不能用于索引定位，只能做过滤。

最左前缀是索引结构决定的，不是优化器的随机选择。

## 覆盖索引

当查询需要的列都包含在索引中时，可以直接从二级索引返回结果，不必回表，称为覆盖索引。
覆盖索引能减少随机 I/O，但会让索引变宽，写放大和存储成本随之上升。

## 常见索引失效场景

- 在索引列上使用函数或表达式，例如 DATE(create_time) = ...；
- 对索引列做隐式类型转换，例如字符串列用数字比较；
- 前导模糊查询 LIKE '%xx'；
- OR 条件中部分列没有索引；
- 优化器估算回表成本过高时主动放弃索引。

索引失效不等于 SQL 一定慢，也不等于优化器有错误，需要结合数据分布和执行计划判断。

## 用 EXPLAIN 判断

EXPLAIN 可以看到访问类型、使用的索引、预估扫描行数和额外信息。
判断慢查询时应同时看实际执行时间、扫描行数和返回行数，不能只凭 type 字段下结论。
统计信息过期会导致优化器估算偏差，必要时更新统计信息后再观察。

## 热点数据行与缓冲池

高频更新同一批数据行时，会出现热点行竞争，表现为锁等待增加、更新变慢。
InnoDB 缓冲池缓存数据页，命中率高时磁盘读减少，但缓冲池不能替代业务层缓存设计；
把大量读请求压到数据库，仍可能造成 CPU 和连接数瓶颈。

## 与缓存方案的分工

索引优化解决数据库内部的查询效率；缓存解决重复读取对数据库的压力。
两者可以叠加，但数据库索引设计不能因为「前面有缓存」就被忽略，
缓存未命中或缓存失效时，最终仍要由数据库承接请求。
