# 分布式锁的适用边界

> 演示资料：本文由 DeepSeek 依据公开的 Redis 缓存通识原创编写，仅用于天机学堂 AI 能力演示，不是任何真实售卖课程的官方讲义，也不代表课程实际授课内容。核验日期：2026-10-31。

## 什么时候需要分布式锁

单机多线程用进程内锁即可。多实例部署、需要跨进程互斥时，才需要分布式锁，
例如同一订单只能被一个实例处理、缓存重建只允许一个实例执行。

分布式锁只解决「互斥」，不解决「业务一定成功」。
拿到锁之后仍要校验业务状态，不能把锁当成幂等或事务的替代品。

## 基于 Redis 的实现要点

- 加锁使用 SET key value NX PX timeout，保证原子性；
- 解锁先比较 value 再删除，通常用 Lua 脚本保证比较和删除的原子性；
- 锁超时要覆盖业务执行时间，并考虑续期；
- 获取失败要有重试上限和退避策略，避免无限重试压垮 Redis。

## 锁超时与续期

如果业务执行超过锁超时，锁会提前释放，其他实例可能同时进入临界区。
常见做法是由持锁线程定期续期（例如 Redisson 的看门狗机制），
但续期依赖进程存活；进程假死、网络分区时仍可能出现两个实例都认为自己持锁。

因此业务侧应尽量让临界区操作短小，并在写操作上使用版本号、唯一约束或幂等键做二次保护。

## 网络分区与主从切换

Redis 主从异步复制时，主节点故障切换可能导致锁信息丢失，出现两个客户端同时持锁。
对正确性要求高的场景，需要评估是否改用具备共识协议的协调组件，
或者用数据库唯一约束、状态机等方案兜底。

不能因为使用了分布式锁就默认系统具备了强一致性。

## 与互斥锁重建缓存的关系

缓存击穿的互斥锁重建，本质上也是一种「只让一个请求回源」的互斥。
如果部署了多个应用实例，这个互斥范围需要跨进程，就要用分布式锁；
如果只是单实例多线程，进程内锁已经足够，不必为了统一而强行引入分布式锁。

选型依据是互斥范围和故障代价，而不是「分布式锁听起来更高级」。
