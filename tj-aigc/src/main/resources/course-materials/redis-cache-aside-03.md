# 缓存旁路模式与数据库一致性

> 演示资料：本文由 DeepSeek 依据公开的 Redis 缓存通识原创编写，仅用于天机学堂 AI 能力演示，不是任何真实售卖课程的官方讲义，也不代表课程实际授课内容。核验日期：2026-10-31。

## 缓存旁路模式（Cache Aside）

读请求先查缓存，命中直接返回；未命中则查数据库，再把结果写回缓存。
写请求先更新数据库，再删除缓存；下一轮读取时重新加载。
这个模式由业务代码显式管理缓存，Redis 不参与业务事务。

## 为什么通常删除缓存而不是更新缓存

- 更新缓存需要构造完整的新值，并发更新时可能写入旧值；
- 删除缓存把「写」简化成一次失效，降低并发覆盖的风险；
- 缓存是否被真正使用不确定，删缓存可以避免为不读的数据做无效计算。

## 先更新数据库再删除缓存的理由

若先删缓存再更新数据库，两个请求交错时可能把旧数据重新写回缓存：
请求 A 删除缓存后还没更新数据库，请求 B 读到旧值并写回缓存，随后 A 才完成更新。

先更新数据库再删除缓存，发生旧值回填的概率更小，但在读写交错和删除失败时仍非绝对一致。
需要更强一致性的场景要在业务层评估加锁、延迟双删或消息补偿，不能默认缓存永远正确。

## 删除失败与延迟双删

删除缓存失败时，可以记录待补偿任务重试，或者设置较短的过期时间兜底。
延迟双删指更新数据库前后各删除一次缓存，中间留出短暂间隔，用来降低并发读回填旧值的概率。
延迟双删不是强一致方案，间隔时间需要结合业务读写耗时评估。

## 过期时间兜底

即使有主动删除，也建议为缓存设置合理过期时间。
过期时间是一致性的最终兜底，但过期时间过短会增加回源压力，过长会放大不一致窗口。
不要把过期时间当作唯一的一致性手段，也不要用永不过期否定竞态问题。

## 与击穿处理的关系

旁路模式解决「读写路径」，击穿解决「热点 key 过期瞬间的集中回源」。
两者可以同时使用：正常读写走旁路，热点 key 重建时用互斥锁收敛回源。
