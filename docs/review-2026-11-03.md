## 三、确认需要修复的缺陷

### H2：领取事务内解密失败使重试次数回滚，可能阻塞后续任务

**位置**

- `tj-aigc/src/main/java/com/tianji/aigc/longterm/UserMemoryStore.java:210-244`：领取事务。
- 同文件 `:225-241`：更新领取状态、递增 attempts、解密任务及读取记忆快照。
- `tj-aigc/src/main/java/com/tianji/aigc/longterm/UserMemoryWorker.java:37-52`：轮询及异常处理。

**现有代码**

```java
                for (Object[] row : claimed) {
                    Payload payload;
                    try { payload = JSON.readValue(cipher.decrypt(first.userId(), (String) row[2]), Payload.class); }
                    catch (Exception error) { throw new IllegalStateException("无法读取待处理轮次", error); }
                    turns.add(new Turn((Long) row[0], (String) row[1], payload.question(), payload.previousQuestion()));
                    attempts = Math.max(attempts, (Integer) row[3]);
                }
                return new Batch(first.userId(), first.sessionId(), first.epoch(), token, List.copyOf(turns), list(first.userId()), attempts);
```

**根因和触发条件**

这是事务边界与失败重试计数耦合的问题。领取事务先将任务改为 RUNNING 并执行 `attempts=attempts+1`，随后在同一个事务内解密。解密或反序列化失败时，运行时异常使整个事务回滚，领取状态和 attempts 都无法落库。

由于异常发生在 claimDue 返回之前，Worker 还未获得 Batch，无法调用正常的 retry(batch) 流程。坏任务满足领取条件、处于优先被处理的位置时，后续轮询会重复命中同一故障组，可能阻塞其他用户任务。

此外，构造 Batch 时的 `list(first.userId())` 会解密已有记忆，也处于领取事务内。修复不能只移动 payload 解密而遗漏快照解密。

**建议修复及最小范围**

在 UserMemoryStore / UserMemoryWorker 边界内，将“领取密文任务并提交”与“解密任务及记忆快照”分开。示意流程如下，方法名不是现有 API：

```java
var claimed = claimEncryptedBatch(); // 事务提交领取状态和 attempts
try {
    return decodeBatch(claimed);     // 事务外解密任务及快照
} catch (RuntimeException error) {
    registerClaimFailure(claimed);   // 按领取令牌登记重试或 FAILED
    return null;
}
```

解码失败仍需能够按 userId、epoch、claim token 定位本次领取结果，保留当前的租约及并发提交保护。不要为跳过坏任务而放松授权或快照一致性约束。

**验收方式**

1. 在隔离测试数据库中准备一个靠前且满足领取条件的坏密文任务，随后准备其他用户的正常任务。
2. 重复领取，确认坏任务 attempts 实际递增，按既有上限进入 FAILED。
3. 确认正常用户任务仍能被后续轮询领取和处理。
4. 分别覆盖任务 payload 损坏、JSON 无法解析、已有记忆 content_cipher 损坏。
5. 回归领取并发、租约失效和 epoch 变化后的提交保护。

**影响面**

主要涉及长期记忆任务领取、解码、失败登记及 Worker 调度。正常聊天可继续的现有降级边界应保留。当前结论是源码机制确认，尚未通过上述故障注入复现。

### H3：未映射异常会绕过 ERROR / STOP 事件

**位置**

`tj-aigc/src/main/java/com/tianji/aigc/service/impl/ChatServiceImpl.java:125-177`，尤其是第 169 行兜底异常分支和第 175 行后的 STOP 拼接。

**现有代码**

```java
                        if (!KnowledgeRetrievalAdvisor.isRetrievalFailure(error)) return Flux.error(error);
                        log.warn("知识库检索失败，会话 {}", sessionId, error);
                        return Flux.just(ChatEventVO.builder().eventType(ChatEventTypeEnum.ERROR.getValue())
                                .eventData(Map.of("code", "KNOWLEDGE_RETRIEVAL_FAILED",
                                        "message", "知识库查询失败，请稍后重试。")).build());
```

**根因和触发条件**

未命中显式错误分类的异常会重新以 Reactor error 信号向下游传播；error 不会触发正常完成后才订阅的 `concatWith(STOP)`。因此，订阅链内未被映射的模型调用异常等可能直接结束连接，没有业务 ERROR / STOP。

这支持“错误契约不完整”的结论，不能单凭这一点定为安全高危。也不应把所有未映射异常都命名为 MODEL_CALL_FAILED，因为其中可能包括其他业务或基础设施异常。

**建议修复及最小范围**

保留已有错误分类和取消分支，对仍未映射的异常记录脱敏日志，并返回通用业务错误事件，继续沿用后续 STOP 拼接。例如：

```java
return Flux.just(ChatEventVO.builder()
        .eventType(ChatEventTypeEnum.ERROR.getValue())
        .eventData(Map.of("code", "CHAT_GENERATION_FAILED",
                "message", "本次生成失败，请稍后重试。"))
        .build());
```

上述代码应放在已识别错误处理之后，不能提前吞掉当前的专用错误码。正常主动停止仍保持停止语义。客户端取消订阅或连接已断开时，无法保证再发送任何终止事件，所以不建议使用“任何路径都保证 ERROR + STOP”的绝对表述。

**验收方式**

- 模拟首 token 前发生模型异常，确认收到通用 ERROR，随后 STOP。
- 模拟已输出部分内容后异常，确认仍有明确终止事件。
- 回归专用错误码、正常完成和用户主动停止。
- 确认失败后释放生成占位，后续请求能够正常取得占位。

**影响面**

涉及 ChatServiceImpl 的 SSE 错误映射及客户端错误码契约。当前结论是源码机制确认，尚未进行真实网络或模型故障注入。

## 四、需要收窄或补证的结论

### M1：Redis 模式约束应同时考虑 A 和 APRIME

`KnowledgeStoreConfig.java:197-200` 的关键词客户端延迟解析中，确实要求 VectorStore 为 Elasticsearch；`KnowledgeRetrievalPipeline.java:58-62,89-100` 会将部分单路异常记录为降级失败。

因此，Redis 存储配合当前混合模式存在配置不匹配的依据。但同一 Pipeline 的第 42 行明确将 `A` 和 `APRIME` 都排除在 hybrid 之外，不能建议一律强制 `store-type=redis ⇒ mode=A`。

建议按照“所选模式是否需要 BM25”建立兼容性校验；在当前实现中至少应保留 A、APRIME 两个纯向量模式。还应确认降级展示范围：现有 INCOMPLETE 标志并不意味着每次有文档的回答都会展示同一条失败提示。

### M2：同步等待问题与实际聊天停止链路需要分开验证

`KnowledgeRetrievalAdvisor.java:81-106` 中，同步 `before().block()` 配合 never 分支可能等待至超时，这一局部机制有依据。现有 `KnowledgeRetrievalAdvisorTimeoutTest` 也明确围绕该行为编写，但本轮没有重新运行。

不过，实际聊天生成链路还包括：

- `ChatServiceImpl.java:197-203`：独立续租心跳检测停止状态。
- 同文件 `:242`：`takeUntilOther(stopped)` 取消生成上游。
- 同文件 `:353-357`：续租检查完成后延迟一秒再重复。

所以不能直接推出“用户停止后必须等满 25 秒”。实际停止延迟还受 Redis 调用等影响，需要在完整 HTTP / SSE 链路测试，不能承诺固定一秒内结束。

如果优化同步调用的取消返回方式，应同时验证不会启动迟到的回答模型调用，不应机械地把所有 never 改成 empty。

### M7：SDK 已有会话失效和重新初始化机制

业务代码的 ready 标志以及 call 阶段缺少显式 invalidate，确实可见于 `CourseMcpClient.java:79-102`。但据此断言“一次闪断等于永久故障”遗漏了 SDK 内部行为。

本轮检查的本地依赖源码为 MCP SDK 0.17.0：

- `HttpClientStreamableHttpTransport.java:215-224`：遇到 McpTransportSessionNotFoundException 时替换失效传输会话，并交给异常处理器。
- `LifecycleInitializer.java:252-261`：清除旧初始化状态，并触发重新初始化。
- `McpAsyncClient.java:318-323`：将传输层异常处理器连接到 initializer。
- `HttpClientStreamableHttpTransport.java:719-728`：resumableStreams 参数说明针对 SSE event id 和流恢复，不能仅凭 false 推导整个客户端永久失去重连能力。

这些源码证据足以否定原报告的推导方式，但不等于已经证明所有故障场景都能恢复。建议补充有会话 ID 的服务端重启、未知会话响应、短暂连接失败后恢复等测试，再决定是否需要业务层重建连接。

测试还需保护现有共享连接边界：不能因某个调用者的取消或预算耗尽，关闭其他调用者正在使用的健康连接。

### M13：缺少自动按 token 裁剪，不等于没有历史 token 检查

`SpringAIConfig.java:91-95` 的 MessageWindowChatMemory 确实按 maxMessages 配置窗口，当前配置为 100 条；这不等于自动满足模型 token 上限。

但 `KnowledgeContextSelector.java:19-35` 的 requestTokens 会遍历 `request.prompt().getInstructions()` 中的消息，并计算已解析工具定义；第 43-45 行再执行总预算检查。因此，知识库链路的这层检查并非只计算 RAG 检索片段。

需要区分三个问题：消息窗口按条数保存、知识库请求已有总预算检查、是否具备自动历史压缩或所有 Agent 的统一预算保护。后两者不是同一能力。

本轮未实测长会话，也未完整核验所有 Agent 的预算覆盖，因此“长会话后所有请求持续失败且只能发几十轮自愈”的影响描述仍需要具体路径和运行证据。
