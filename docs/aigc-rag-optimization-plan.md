# 天机学堂知识库 RAG 优化：最终实施方案

制定日期：2026-10-24。

本文供新的开发窗口直接执行。范围是 `D:\Java\tianji` 中的知识库问答优化，配套固定评测与 Langfuse 观测。目标是证明哪些改动改善了真实问题，并保持现有业务语义。

## 1. 已确定的范围与工作规则

- 保留 Spring AI 1.1.2、现有 Spring Boot 和 Elasticsearch 客户端技术栈，不进行无关升级。
- 复用现有查询改写，增加 BM25 与向量混合检索、应用层 RRF、可开关的专用 rerank、保守的上下文处理。
- Langfuse 接入与固定评测属于本轮交付。基础追踪前期建设，随各阶段补齐。
- 父子级召回、GraphRAG、生成式摘要压缩、自动多轮补查、新 Agent、大规模知识库重构不在本轮范围内。
- 课程导购保持现有业务行为；价格、有效期等实时事实继续由课程业务接口核实。
- 保留 Agent 路由、SSE、请求取消、请求归属、会话权限及聊天记忆语义。允许为集成增加必要代码，不进行无关重构。
- 开始时检查分支、工作区与适用的项目指导文件，保留全部无关改动。未经明确要求，不提交、不推送、不部署。
- 分阶段实现、测试和报告；在已授权范围内完成可继续的工作，不把每个阶段结束变成额外审批点。
- 外部服务不可用时继续完成不依赖它的工作，明确列出真实联调缺口；不得以 Mock 通过代替真实服务验收。

能力实现、真实联调和默认启用分别报告。未证明收益的处理策略可以保持关闭；不能因此将尚未实现或尚未验证的能力标记为完成。

## 2. 已知起点与必须重新核实的事项

## 3. 目标链路

```text
核实登录身份、会话归属、知识库访问权限
                 ↓
固定本次服务端授权文档范围
                 ↓
用户原问题＋必要历史 → 查询改写
                 ├─ CLARIFY：按现有语义返回澄清
                 ├─ 失败：按现有语义返回改写错误
                 └─ KEEP / REWRITE
                            ↓
               BM25 检索 ＋ 向量检索
               两路均在检索阶段过滤授权范围
                            ↓
                 应用层 RRF 融合与去重
                            ↓
                    专用 rerank
                            ↓
              完整片段选择、去重与预算控制
                            ↓
                空证据等确定性边界检查
                            ↓
               围绕用户原问题、根据证据回答
                            ↓
                 现有 SSE 与记忆保存流程
```

Langfuse 横向记录阶段、证据、异常和实验信息。本轮不增加独立的 LLM 证据充分性判定调用。非空资料是否真正覆盖问题，通过回答约束、人工评审和评测验证，不把相关性分数当作充分性保证。

## 4. 检索与回答的实现要求

### 4.1 查询改写与授权

- 复用 KEEP、REWRITE、CLARIFY，保留现有失败处理和错误事件。
- 不默认增加原问题与改写问题的双查询，不新增自动改写回退。
- 改写不得创造实体、数字、否定条件或用户需求；用多轮案例验证条件保留。
- 授权检查先于改写模型调用。后续阶段复用已确认的范围，不在工作线程中重新依赖请求线程的 ThreadLocal。
- 可信权限不得来自模型、客户端过滤表达式或检索资料。
- 本轮维持既有权限检查时点；不额外承诺实时撤销权限的新机制。权限变更按现有时点与策略测试。

### 4.2 BM25 与向量混合检索

- 先核实实际 ES 版本、索引 Mapping、中文分词、向量维度、相似度和数据规模，以及 Nacos 等配置覆盖。
- 关键词检索和向量检索尽量复用现有 ES 客户端和存储，不替换整套向量存储。
- BM25 与向量两路使用等价的服务端过滤，在检索阶段生效；不能先跨范围召回再过滤。
- 检查真实术语的分词效果，再决定是否调整 analyzer；不默认安装新分词插件。
- 优先采用应用层 RRF，不要求 ES 原生 RRF，也不因此引入新的许可依赖。
- 查询并发按现有客户端、调度和取消能力选择，不强制为了并行增加复杂编排。
- 向量候选数量、阈值和最终上下文选择数量分别管理，先进行参数对照。

### 4.3 融合身份与 RRF

- 每路内部先消除同一片段的重复结果，避免同一路重复加分。
- 采用稳定的片段身份。优先复用现有 ID，并核验文档 ID、内容版本、片段序号和索引代际的一致性；不要仅按文本相似去重。
- 同一片段在两路中的排名贡献累加，最终输出一个候选。不能先删除跨路重复项而丢失贡献。
- 保留来源、原始排名与必要分数；BM25 分数、向量相似度和融合分数使用独立字段。
- RRF 使用 `sum(1 / (rankConstant + rank))`，排名从 1 开始；两路初始等权，`rankConstant` 和融合候选上限可配置。
- 使用确定的同分处理规则，便于重复实验。RRF 分数不作为回答置信度。

### 4.4 Rerank

- 使用专用重排序模型；根据现有模型服务核实模型、地域、权限、接口、费用及输入限制后选定具体接入方式。
- 不把聊天或 embedding 可用视为 rerank 已可用；不为此替换现有聊天模型。
- 校验返回的候选序号或身份、重复项、缺失项及分数合法性，按原候选取回证据，不能信任返回文本替换来源。
- 启用开关、模型、调用超时、输入候选上限、输出保留数量可配置；阈值仅在模型语义及评测支持时启用，默认不强加通用阈值。
- 高分只能表示该模型下的相关性，不表示事实正确或答案充分。

### 4.5 上下文处理

- 本轮正式实现非生成式上下文处理；短资料可以原样通过，压缩比例不设硬指标。
- 第一版以稳定身份去重、完整片段选择和预算控制为主。只在边界清晰时选择完整段落，暂不实现通用句子级语义裁剪或生成式摘要。
- 相似内容若版本、来源或适用条件不同，不能直接合并。准确标识重复后才移除，保留出处关系。
- 不从片段中单独摘出数字或结论而丢失条件、否定和例外；不使用任意字符截断拼接。
- Token 预算包括系统提示词、必要历史、用户问题、资料、实际存在的工具协议开销，以及预留输出和安全余量。
- 尽量使用兼容模型的 Token 估算；无法精确计算时标记为估算，避免宣称精确用量。
- 按相关性与预算选择证据，同时防止重复片段挤占不同必要事实。放不下完整关键证据时，缩小可回答范围或说明不足。
- 在最终请求组装处检查完整预算。若系统提示词、必要历史、用户原问题和输出预留本身已超预算，应按现有错误协议清楚说明上下文过长并停止本次生成；不静默删除必要历史、截断用户条件或发送已知超限的模型请求。
- 用例验证是保留事实条件的依据，不声称普通文本算法能保证识别全部语义条件。

### 4.6 失败、取消和证据不足

| 情况 | 处理要求 |
| --- | --- |
| 一路普通检索故障、另一路成功 | 可使用成功且已授权的结果继续，记录单路降级；成功返回空列表不等于调用失败 |
| 一路故障、另一路成功但为空 | 可返回本次暂无法取得足够资料的保守说明，记录检索不完整；不能归类为两路正常的无答案结果，也不能断言知识库确无资料 |
| 两路检索均失败 | 返回检索错误，不伪装成知识库无答案 |
| 两路正常但没有候选 | 保持明确的资料不足行为 |
| rerank 普通故障、超时或响应非法 | 请求仍有效且预算允许时，回退已授权的融合候选，并执行同样的上下文预算处理 |
| 权限错误、请求失效、用户取消 | 终止；不能触发单路检索或 rerank 回退 |
| 无法得到足够支持的结论 | 按现有澄清与回答约束处理，说明缺失或仅回答可确认部分 |

- 每个新增外部调用设置实际客户端超时，定义检索准备阶段的耗时预算；同步入口超时不能当成 SSE 全流程超时。
- 已取消、失去归属或超出预算的请求，不启动新的降级、生成或保存任务。
- 阻塞调用不能立即停止时，返回后丢弃迟到结果。新增阶段沿用现有有效性及归属检查。
- 不新增跨会话共享的可变候选集合或答案缓存。
- 错误信息对用户保持必要且脱敏；详细原因进入内部观测，不把工具过程塞进最终回答。

## 5. Langfuse 的最小落地

- 复用 Spring AI 1.1.2 Observability、Micrometer、OpenTelemetry 与现有配置体系。
- 核查手工创建的模型和向量存储是否接入真实 ObservationRegistry；使用框架已有观测，补业务步骤，不重复记录同一次调用。
- 一个问答请求使用一个 trace，多个请求按会话关联；每轮保留自己的请求或 generation 标识。
- 至少关联：改写、关键词召回、向量召回、融合、rerank、上下文处理和回答生成。不开启或没有执行的阶段按实际状态记录。
- 框架模型观测尽量获取模型标识、耗时和可获得的用量；融合排名、证据选择、降级原因、配置版本等通过必要的自定义埋点补齐。
- 候选 ID、会话 ID 等高基数信息用于 trace 属性，不作为无界 metrics 标签。
- 验证 Reactor、boundedElastic 和 SSE 下的上下文传播；成功、失败、取消都应正确结束对应观测，不留下悬空 span。
- 导出使用异步、有限队列与有限超时；服务故障不阻塞问答，不在每次 SSE 输出时同步刷新。
- 凭据不入 trace；原文采集最小化、可配置且脱敏。评测样本可在受控范围采集必要内容，普通用户对话不默认全量上传。
- 固定记录实验 ID、代码版本、Prompt/配置版本和数据版本；模型用量不可得时标记缺失，不用猜测的值填充。
- 优先连接已存在且获授权的实例。没有可用实例或凭据时，完成接入配置、必要测试及运行说明，继续其他开发，并明确真实联调未完成；不自行部署新基础设施。

真实验收必须在 Langfuse 中查到一次完整请求，并核对阶段关联、最终状态及数据映射。Exporter 初始化成功或日志显示发送不能单独代表通过。

## 6. 固定评测与实验

### 6.1 数据与执行方式

- 目标为约 30～50 个真实案例；实际资料不足时建立更小但有效的集合，不用虚构业务内容补数。
- 每例记录：ID、类型、原问题、必要历史、授权范围、参考证据及版本、预期要点、禁止事实和澄清或资料不足要求。
- 覆盖直接提问、同义表达、连续追问、多条件和否定、数字与例外、无答案、授权隔离；版本冲突仅在实际资料存在时纳入真实评测。
- 技术测试可以使用隔离的合成夹具验证权限、冲突和异常，但必须与真实业务评测分开标识。
- 评测调用生产使用的检索或问答实现，避免另写一份仅用于打分的平行逻辑。
- 每个案例和模式使用隔离的会话历史，禁止前一个实验的回答污染下一个实验。
- 数据集、配置快照和脱敏报告可存于 `docs/rag-evaluation/`；未脱敏对话、凭据和临时原始响应不进入版本管理。

### 6.2 实验模式

| 模式 | 改动 |
| --- | --- |
| A | 当前原始链路及配置，保存其真实基线 |
| A′ | 仅调整向量 topK 与相似度阈值，沿用原有片段处理算法 |
| B | 在明确冻结的 A 或 A′ 配置上增加 BM25 与 RRF |
| C | 在 B 上增加 rerank |
| D | 在 C 上增加本轮上下文处理 |

- 尽量固定聊天模型、生成参数、Prompt、数据、授权范围和观测配置；各模式的候选数量与实际上下文大小必须记录。
- B 默认继承经验证优于 A 的 A′ 配置；A′ 未显示收益时继承 A。记录具体配置版本，C 继承该 B，D 继承该 C；不在后续模式中暗中重新调参。
- 区分扩大召回、增加关键词路径、重排序和上下文处理的增量收益，不同时修改多个变量后归因给某一模块。
- 评测只改变该模式声明的处理；原始基线不悄悄应用新压缩。公共的权限与生命周期保证在所有模式中保留。
- 短资料下 D 可以与 C 相同，如实报告无压缩需求；不为了展示收益制造冗余。
- 对有波动的重要案例重复运行，记录外部模型标识和运行时间，不承诺逐字确定性。
- rerank 真实服务不可用时，可用 B 的结果继续验证上下文处理，单独标记为“B＋上下文处理”补充实验。故障回退或 Mock 结果不得冒充完整 C/D 的正常真实实测，也不能据此宣称验证了二者的联合收益。

### 6.3 指标与判定

- 检索：参考证据命中；标注充分时计算 Recall@K、MRR@K。多证据问题另外检查必要事实覆盖，不能只看第一条相关结果。
- 上下文：必要证据是否保留、是否丢失条件或引入冲突、估算 Token 和来源可追溯性。
- 回答：事实正确、依据一致、必要条件覆盖，以及无答案时的处理是否恰当。
- 工程：阶段与总耗时、首字等待、可获得的用量、失败和降级；权限与取消单独验证。
- 数值、身份和确定性条件优先程序校验；语义质量结合人工与模型评分，模型裁判先用人工标注校准。
- 保存逐例结果、失败原因与汇总。小样本 p50/p95 仅作描述，不作为充分生产效果证明。
- 调参案例与最终验证案例尽可能分开；样本太少时明确说明调参偏差风险，不把同一批反复调优后的分数宣称为泛化效果。
- 启用前比较收益与额外延迟；权限越界、失效请求污染或关键事实错误不能被平均分提升抵消。没有明确收益时保留能力但关闭对应策略，说明依据。

## 7. 代码边界

| 位置 | 职责 |
| --- | --- |
| KnowledgeQueryRewriter | 保留现有改写与澄清，不承载检索和权限决策 |
| KnowledgeDocumentService | 文档导入、切分和元数据，本轮不强制改变切分结构 |
| 小型检索组件 | BM25、向量查询及融合，接收可信授权范围 |
| 小型 rerank 组件 | 外部调用、结果校验和必要局部恢复 |
| 上下文处理代码 | 去重、完整片段选择、预算及证据来源 |
| KnowledgeRetrievalAdvisor | 串联步骤、检查有效性、增强原问题请求与整理响应 |
| 观测配置与必要埋点 | 复用框架观测并关联业务阶段和实验 |

职责不等于必须新增同等数量的接口。简单纯函数可以留作方法，不做通用检索框架或复杂策略引擎，也不把所有新逻辑堆到 Advisor。

新增参数优先按“检索、rerank、上下文、观测”分组；只暴露实际需要调试的选项，不为理论组合增加配置。用固定的实验配置快照支持 A/A′/B/C/D，不依赖大量任意开关组合。

如确需改 Mapping、切分或 embedding 配置，使用新索引/明确代际，验证后切换配置并保留旧索引回退。不得覆盖或删除既有数据。内容哈希不能替代切分策略、embedding 配置和索引版本的完整记录。

## 8. 实施顺序与阶段验收

1. **审计与基线**：重新核实代码、运行配置和数据；建立真实案例、A 结果及必要追踪。交付已确认事实、外部缺口和逐例失败分类。

3. **混合检索**：完成 B；验证过滤一致、融合加分、稳定身份、同分处理和单路故障。用真实案例解释增加了哪些有效证据。
4. **重排序**：完成 C；验证真实接口、响应映射、输入限制、普通故障回退，以及取消后不启动回退或生成。报告额外延迟。
5. **上下文处理**：完成 D；验证完整片段、预算余量、条件与来源保留，以及短资料原样通过。对照 C 报告增量效果。

每阶段都运行与修改直接相关的测试，再推进下一阶段；已有通过检查无需无故反复扩跑。新增测试保护真实行为，避免只镜像实现。

记录每阶段：改动及原因、实际运行检查、逐例效果、耗时与用量变化、风险、回退路径和待验证事项。区分测试未运行、Mock 通过、集成通过和真实模型通过。
