## 运行关系

1. 积分消费者调用 `PointsRecordServiceImpl.addPointsRecord()`，在用户锁内完成每日额度判断。
2. `PointsMessageServiceImpl.savePointsRecord()` 在独立代理方法的事务中一起插入明细与同步任务；提交后才释放用户锁。
3. 原有 `PointsMessagePublishTask` 每秒处理待办消息。`points.board.sync` 在本地执行，不发送到 RabbitMQ；其余业务消息继续按原来的 Broker 确认流程发送。
4. 同步任务按原始入账月份汇总该用户所有积分类型，使用 ZADD 设置总额。Redis 或完成标记失败时，待办记录保留，重复同步不会重复累加。
5. 三个 XXL-JOB handler 名称不变，仍按“建表 → 持久化 → 清理”执行。清理本身会校验完整性，错误执行顺序会失败并保留源数据。

## 部署与边界

- 复用已存在的消息表及唯一索引，无需增加数据库表或字段。所有 learning-service 实例需要运行同一版本，再执行归档任务。
- 相较原链路，月榜更新增加一次本地任务轮询，正常约一秒；归档读锁占用期间同步会等待或重试，消息积压、故障也会增加延迟。
- 历史列表依据历史表是否存在筛选；刚创建、仍在归档的赛季可能暂时显示部分数据。清理前会做完整校验。
- 笔记新消息示例：`{"userId":1,"noteId":77}`；评论新消息示例：`{"userId":1,"commentId":88}`。当前仓库未实现这两类业务生产端，本次修复消费者契约与兼容路径。
- 已入账但发生于本次修复前的漏分，不会凭空生成同步任务；如需修复既有数据，应另行核对后补建待办记录。手工 Redis 联调积分也不是数据库月积分的事实来源。
- 连续签到仍按本月统计，不改变既有 7 / 14 / 28 天奖励规则。
